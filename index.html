Starfield 1.16.244 (Steam) · reverse engineering plus an in-game test · checked 2026-11-21 · page built 2026-11-21 21:33 UTC

Do Vortex mods and Creations really have separate load orders?

A Facebook comment claimed that Vortex mods load through the script extender, that Creations load when you load a save, and that this gives Starfield two load orders. We checked the claim twice: by reading the game's own code, and by watching Plugins.txt in the game step by step. This page shows every step, what each one found, and how you can repeat the test on your own PC.

By Richard Bejtlich, Richard Presents Starfield Essentials on YouTube

More Starfield tools and references are on the Richard Presents Development Hub.

1load order: Creations and other plugins share one Plugins.txt
0times Plugins.txt changed when a save was loaded (Continue and Load)
2places in Starfield.exe that rewrite Plugins.txt: the Creations sync and the Creations menu
7in-game snapshots, including a control step that proved the test catches a rewrite

TL;DR

I tested this. I RE'd the game's code (Starfield.exe 1.16.244) and snapshotted Plugins.txt in game during a series of tests.

  • Starfield reads Plugins.txt itself at startup, so Vortex and MO2 plugins load without SFSE. SFSE is for DLL plugins.
  • Creations aren't loaded from your save. They're in the same Plugins.txt as your other mods: one list, one load order.
  • Loading a save (Continue or Load) didn't change Plugins.txt at all. A save only records which plugins it used.
  • The game does rewrite Plugins.txt at every launch and when you reorder Creations in game. In my test it kept every mod and only moved what I moved.

The conflict isn't two load orders. It's two tools editing one file: if you reorder in game and your mod manager later deploys its own order, one undoes the other. Manage the order in one place.

This is Richard's reply to the comment, word for word. The rest of the page shows the evidence behind each sentence.

What's new

  • 2026-11-21. This page went live, with the code check, the in-game test, the scripts and the verdicts.

The claim

Vortex mods load when you start the game via the script extender. Creations load when you load the character save. This means load orders are managed seperatly. This is what creates most conflicts. I make mods and this is something that we must account for.

The comment was posted on Facebook by a mod author. We quote it as written. It makes three testable claims: Vortex mods depend on the script extender, Creations load from the save, and the two have separate load orders.

Verdict, claim by claim

ClaimVerdictEvidence
Vortex mods load via the script extender.FalseStarfield.exe has its own Plugins.txt reader, and the game's startup code calls it. SFSE describes itself as mostly a loader for its own DLL plugins. SFSE also only supports the Steam version, yet Game Pass players load mods from Plugins.txt too.
Creations load when you load the character save.FalseCreations are plugin files in the Data folder, listed in the same Plugins.txt. The game reads that list at startup, before the main menu. In the test, loading two different saves didn't touch Plugins.txt.
Load orders are managed separately.FalseThere's one list in the game and one file on disk. The Creations code looks up each Creation's plugin in the same file list as every other plugin, writes them all to the same Plugins.txt, and rebuilds the list from it.
This is what creates most conflicts.Partly trueThere is a real conflict, but it comes from two tools editing one file. The game rewrites Plugins.txt at every launch and after an in-game reorder, and your mod manager writes its own order when it deploys.
We must account for it.TrueManage the order in one place, and check it again after you change Creations in the game.

Complete conclusion

  • There is one load order. Starfield keeps one list of plugins and one file on disk, Plugins.txt. Creations are ordinary plugin files in the Data folder, and they sit in that list with every other plugin. ContentCatalog.txt only records which Creations are installed.
  • The game reads Plugins.txt itself, at startup. The reader is part of Starfield.exe and runs from the game's start-up code. The script extender isn't needed for .esm, .esp or .esl plugins. SFSE loads DLL plugins.
  • Loading a save doesn't load or reorder plugins. Continue and Load left Plugins.txt untouched. A save only records which plugins it used, so the game can warn you when one is missing.
  • The game rewrites Plugins.txt at every launch, before the main menu, and again whenever you change Creations in the in-game menu. In the test, both rewrites kept every plugin. The launch rewrite changed nothing, and the menu rewrite moved only what was moved. Anything that isn't a plugin line, such as a comment, is dropped.
  • The real conflict is two tools editing one file. If you reorder in the game and your mod manager later deploys its own order, the last one to write wins. Manage the order in one place, and check it again after you change Creations in the game.

Part 1: the game's code

We loaded Starfield.exe 1.16.244, the same build the test ran on, into Ghidra with the Bethesda Ghidra Scripts names, and queried it read-only with GhidraSQL. The addresses below are for that build and will move in other versions. The page describes what the code does and shows none of it.

  1. 1

    Find the file names in the executable

    Game file

    What we did. We searched Starfield.exe's strings for the load-order file names and the old INI settings.

    What it showed. The executable holds %sPlugins.txt, %sContentCatalog.txt, the ten sTestFile1 to sTestFile10 settings of the [General] INI section (the old way to load a plugin without Plugins.txt) and bInvalidateOlderFiles. Two functions use the Plugins.txt name, and one uses the ContentCatalog.txt name.

  2. 2

    Read the first Plugins.txt function: the reader

    Game file

    What we did. We decompiled the function at 0x140425310.

    What it showed. It opens Plugins.txt for reading and reads it a line at a time. It skips lines that start with # and lines that are too short. When it's asked for active plugins only, it keeps only lines that start with * and drops the star. It adds each remaining name to the game's list of files. This is the game's own code, not the script extender's.

  3. 3

    Follow the reader back to startup

    Game file

    What we did. We listed the reader's callers, then their callers, until we reached code we could identify.

    What it showed. One path starts in the game's start-up function (0x141898870), the same function that reads Starfield.ini, StarfieldCustom.ini and StarfieldPrefs.ini and checks the storefront. A second path runs through the function that loads Starfield.esm (0x141883440) and the function that builds TESDataHandler's file list (0x140598750). Both run when the game starts, before any save is loaded.

  4. 4

    Read the second Plugins.txt function: the writer

    Game file

    What we did. We decompiled the function at 0x140424dc0.

    What it showed. It clears the file's read-only flag, deletes Plugins.txt and creates a new one. It writes the two-line header ("This file is used by Starfield to keep track of your downloaded content. Please do not modify this file."), then one line per plugin in the list it is given, with a * in front of active ones. It skips TestData.esm and the game's built-in files. Anything else in the old file, such as a comment line, is gone after a rewrite.

  5. 5

    Find who calls the writer

    Game file

    What we did. We listed every caller of the writer.

    What it showed. There are exactly two. One is the Creations sync (0x14218bb40) in the game's UserContent code, which has eight callers of its own. The other is a menu function (0x141ecdc70) reached from MainMenu: the Creations menu on the main menu. No other code writes Plugins.txt.

  6. 6

    Read the Creations sync

    Game file

    What we did. We decompiled the Creations sync.

    What it showed. For each Creation, it takes the Creation's .esm, .esp or .esl files and looks each one up in TESDataHandler's list, the same list that holds every other plugin. Then it calls the writer and runs the list builder again, so the new order takes effect. Creations and manually installed plugins share one list and one file.

  7. 7

    Check ContentCatalog.txt

    Game file

    What we did. We followed the ContentCatalog.txt name to its function (0x142183f00).

    What it showed. It belongs to the same UserContent code, next to a function that names the Creations data folder. ContentCatalog.txt is a JSON file that records which Creations are installed (title, version, files, timestamp). It doesn't hold the load order.

  8. 8

    Look for a path from loading a save

    Game file

    What we did. We looked for any path from save loading to the writer.

    What it showed. We found none, and a save only stores the list of plugins it was made with. Code alone can't rule out every indirect call, so the in-game test checked this directly.

Part 2: the in-game test

The code showed what can happen. The test showed what does happen. A script copied Plugins.txt, ContentCatalog.txt and StarfieldCustom.ini after each step, along with each file's modified time and SHA256 checksum. Vortex was closed for the whole test, so only the game could change the files.

The marker line. Before the first launch the script added one comment line to Plugins.txt. The game's reader skips lines that start with #, so the line is harmless. The writer only writes its own header and plugin lines, so if the marker vanished, the game had rewritten the file. After the marker was gone, the file's modified time was the signal, because the writer deletes the file and creates it again.

The control. Step 06 reorders a Creation, which the code says must rewrite the file. It did. That shows the test can see a rewrite when one happens, so the quiet steps really were quiet.

What we got wrong along the way

We started with a draft reply and changed it as the evidence came in. These are the three changes, so you can judge the method as well as the result.

  • "Since the mid-2024 update." An early draft of the reply dated the native Plugins.txt support to a mid-2024 patch. That came from memory and a forum post, not from patch notes, so the reply now says "on current versions" and the code check stands in for the date.
  • "The game rewrites Plugins.txt when you load a save." Several players report this. The code showed no such path, and the test didn't reproduce it on this setup: Continue and Load left Plugins.txt alone. What does change on the first Continue is ContentCatalog.txt (timestamps only), which may be what people noticed.
  • "Only Creations changes rewrite the file." The code check found the Creations sync and the Creations menu as the only writers, and we first read that as "only when you change Creations". The test showed that the Creations sync also runs at every launch, so the game rewrites Plugins.txt every time it starts.

Limits

  • The test ran once, on one PC, with the Steam version 1.16.244, Vortex closed, and one set of installed Creations.
  • We didn't test what Vortex or MO2 does on its next deploy after an in-game reorder. That's where two managers would really fight.
  • MO2 normally gives the game its own copy of Plugins.txt through its virtual file system, so the file this script reads may not be the one the game sees when you start it from MO2.
  • We didn't test the Game Pass version or a Plugins.txt line for a plugin file that's missing.
  • We didn't trace all eight callers of the Creations sync, so other moments may also trigger a rewrite. The launch rewrite is the one the test caught.

What this means for your mod setup

  • Pick one place to manage the order: your mod manager or the in-game Creations menu, not both.
  • After you change Creations in the game, open your mod manager and check the order before you play, or deploy again from the mod manager.
  • Don't put notes in Plugins.txt. The game deletes comment lines when it rewrites the file.
  • If a save says content is missing, the fix is in Plugins.txt and the Data folder, not in the save. The save only lists what it was made with.

Run it yourself

You need Windows PowerShell (built into Windows) and, for the comparison, Python 3.9 or later. Save both scripts from this page (or from the repository) in one folder. Close Vortex or MO2 first, so only the game can change the files. Run the snapshot script from the Windows account you play on. Its output goes to PluginsTxtTest on your Desktop unless you add -OutDir.

# 0. Before starting the game: first snapshot, and add the marker line
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 00-start -AddMarker

# After each step in the game, Alt-Tab out and take a snapshot
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 01-menu
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 02-creations-look
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 03-continue
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 04-load-save
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 05-quit
powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 06-creations-change

# Then compare the steps
python compare_snapshots.py

If a result looks wrong, add -Verbose to a snapshot command. It prints and logs each file it read or couldn't find to snapshot.log in the output folder. python compare_snapshots.py --verbose writes compare.log there too.

Afterward, deploy from your mod manager again to put back its order. The marker line is harmless if it's still there, and a copy of the original Plugins.txt is in PluginsTxtTest\Plugins.txt.backup.

PluginsTxtSnapshot.ps1 (MIT license)
<#
.SYNOPSIS
  Copy Starfield's load-order files after one test step, with times and checksums.

.DESCRIPTION
  Copies Plugins.txt and ContentCatalog.txt (from %LOCALAPPDATA%\Starfield) and StarfieldCustom.ini (from
  Documents\My Games\Starfield) into <OutDir>\<Step>\, and writes info.txt there with each file's modified time,
  size and SHA256. It only reads those files, except with -AddMarker.

  -AddMarker (use it on the first step only) backs up Plugins.txt to <OutDir>\Plugins.txt.backup, then adds one
  comment line. The game ignores lines that start with #, but when it rewrites Plugins.txt it writes only its own
  header and plugin lines, so the marker disappearing means the game rewrote the file.

  Run it from the Windows account you play on: it reads that account's own folders.

.EXAMPLE
  powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 00-start -AddMarker

.EXAMPLE
  powershell -ExecutionPolicy Bypass -File .\PluginsTxtSnapshot.ps1 01-menu -Verbose
#>
[CmdletBinding()]
param(
  [Parameter(Mandatory = $true, Position = 0)][string]$Step,
  [switch]$AddMarker,
  [string]$OutDir = (Join-Path ([Environment]::GetFolderPath('Desktop')) 'PluginsTxtTest')
)
$ErrorActionPreference = 'Stop'

if ($Step -notmatch '^[A-Za-z0-9._-]+$') {
  [Console]::Error.WriteLine("PluginsTxtSnapshot: step name '$Step' can only use letters, digits, dots, dashes and underscores (for example 01-menu).")
  exit 2
}

$app   = Join-Path $env:LOCALAPPDATA 'Starfield'
$docs  = Join-Path ([Environment]::GetFolderPath('MyDocuments')) 'My Games\Starfield'
$files = @(
  (Join-Path $app  'Plugins.txt'),
  (Join-Path $app  'ContentCatalog.txt'),
  (Join-Path $docs 'StarfieldCustom.ini')
)
$plugins = $files[0]
$marker  = '# PluginsTxtSnapshot marker - safe to delete'
$out     = Join-Path $OutDir $Step
$log     = Join-Path $OutDir 'snapshot.log'

New-Item -ItemType Directory -Force $out | Out-Null

function Write-Log([string]$Text) {
  Write-Verbose $Text
  if ($VerbosePreference -ne 'SilentlyContinue') {
    Add-Content -Path $log -Value "$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss') [$Step] $Text"
  }
}

Write-Log "Output folder: $out"
Write-Log "Reading Plugins.txt and ContentCatalog.txt from $app; StarfieldCustom.ini from $docs"

if ($AddMarker) {
  if (-not (Test-Path $plugins)) {
    [Console]::Error.WriteLine("PluginsTxtSnapshot: no Plugins.txt at $plugins. Start Starfield once so it creates the file, then run this again.")
    exit 1
  }
  $backup = Join-Path $OutDir 'Plugins.txt.backup'
  Copy-Item $plugins $backup -Force
  Add-Content -Path $plugins -Value $marker
  Write-Host "Backed up Plugins.txt to $backup and added the marker line."
  Write-Log "Marker added; backup at $backup"
}

$info = @(
  "Step: $Step",
  "Taken: $(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')",
  "Starfield running: $([bool](Get-Process Starfield -ErrorAction SilentlyContinue))",
  "Vortex running: $([bool](Get-Process Vortex -ErrorAction SilentlyContinue))",
  "Mod Organizer running: $([bool](Get-Process ModOrganizer -ErrorAction SilentlyContinue))",
  ""
)
foreach ($f in $files) {
  if (Test-Path $f) {
    $i = Get-Item $f
    Copy-Item $f $out -Force
    $line = "$($i.Name): modified $($i.LastWriteTime.ToString('yyyy-MM-dd HH:mm:ss')), $($i.Length) bytes, SHA256 $((Get-FileHash $f).Hash)"
    Write-Log "Copied $f"
  } else {
    $line = "$(Split-Path $f -Leaf): not found at $f"
    Write-Log "Not found: $f"
  }
  $info += $line
}
if (Test-Path $plugins) {
  $info += '', "Marker line present: $((Get-Content $plugins) -contains $marker)"
}
$info | Set-Content (Join-Path $out 'info.txt')
$info | ForEach-Object { Write-Host $_ }
Write-Host "Saved to $out"
exit 0
compare_snapshots.py (MIT license)
"""Compare the step folders made by PluginsTxtSnapshot.ps1.

For each pair of steps in name order it reports:
  - whether Plugins.txt was rewritten (its modified time changed) and how its lines changed,
  - whether ContentCatalog.txt changed, field by field.

Usage:
  python compare_snapshots.py [FOLDER] [--verbose]

FOLDER defaults to PluginsTxtTest on your Desktop. --verbose also writes compare.log in FOLDER.
Exit codes: 0 compared; 1 folder missing or fewer than two steps; 2 wrong arguments.
It only reads the snapshot folders.
"""
import argparse
import difflib
import json
import os
import re
import sys
from pathlib import Path

LOG = []


def log(msg):
    LOG.append(msg)


def lines(p):
    if not p.exists():
        return None
    return p.read_text(encoding="utf-8", errors="replace").splitlines()


def mtime(step, name):
    info = step / "info.txt"
    if not info.exists():
        return None
    m = re.search(re.escape(name) + r": modified ([0-9-]+ [0-9:]+)", info.read_text(encoding="utf-8", errors="replace"))
    return m.group(1) if m else None


def catalog_diff(pa, pb):
    try:
        ja = json.loads(pa.read_text(encoding="utf-8"))
        jb = json.loads(pb.read_text(encoding="utf-8"))
    except (OSError, ValueError) as ex:
        return [f"    could not read as JSON ({ex}); compare the two files by hand"]
    out = []
    for k in sorted(set(ja) | set(jb)):
        va, vb = ja.get(k), jb.get(k)
        if va == vb:
            continue
        if isinstance(va, dict) and isinstance(vb, dict):
            fields = [f for f in sorted(set(va) | set(vb)) if va.get(f) != vb.get(f)]
            out.append(f"    {k}: {', '.join(fields)} changed")
        else:
            out.append(f"    {k}: {'added' if va is None else 'removed' if vb is None else 'changed'}")
    return out


def compare(a, b):
    print(f"===== {a.name} -> {b.name}")
    ta, tb = mtime(a, "Plugins.txt"), mtime(b, "Plugins.txt")
    pa, pb = lines(a / "Plugins.txt"), lines(b / "Plugins.txt")
    log(f"{a.name} -> {b.name}: Plugins.txt modified {ta} -> {tb}")
    if pa is None or pb is None:
        print("Plugins.txt: missing from one of the steps")
    else:
        rewritten = ta != tb
        if pa == pb:
            print(f"Plugins.txt: {'rewritten (new modified time), same text' if rewritten else 'not rewritten'}")
        else:
            kind = "same lines, new order" if sorted(pa) == sorted(pb) else "lines added or removed"
            print(f"Plugins.txt: rewritten ({kind})")
            for d in difflib.unified_diff(pa, pb, lineterm="", n=0):
                if d.startswith(("+", "-")) and not d.startswith(("+++", "---")):
                    print("   ", d)
    ca, cb = a / "ContentCatalog.txt", b / "ContentCatalog.txt"
    if ca.exists() and cb.exists():
        if ca.read_bytes() == cb.read_bytes():
            print("ContentCatalog.txt: not changed")
        else:
            print("ContentCatalog.txt: changed")
            for d in catalog_diff(ca, cb):
                print(d)
    else:
        print("ContentCatalog.txt: missing from one of the steps")


def main(argv):
    desk = Path(os.path.expanduser("~")) / "Desktop" / "PluginsTxtTest"
    ap = argparse.ArgumentParser(description="Compare PluginsTxtSnapshot.ps1 step folders.")
    ap.add_argument("folder", nargs="?", default=str(desk), help="snapshot folder (default: %(default)s)")
    ap.add_argument("--verbose", action="store_true", help="also write compare.log in the folder")
    args = ap.parse_args(argv)
    root = Path(args.folder)
    if not root.is_dir():
        print(f"compare_snapshots: folder not found: {root}. Pass the folder PluginsTxtSnapshot.ps1 wrote to.",
              file=sys.stderr)
        return 1
    steps = sorted(p for p in root.iterdir() if p.is_dir())
    log(f"folder {root}: steps {[s.name for s in steps]}")
    if len(steps) < 2:
        print(f"compare_snapshots: {root} has {len(steps)} step folder(s); take at least two snapshots first.",
              file=sys.stderr)
        return 1
    for a, b in zip(steps, steps[1:]):
        compare(a, b)
    if args.verbose:
        (root / "compare.log").write_text("\n".join(LOG) + "\n", encoding="utf-8")
        print(f"log: {root / 'compare.log'}")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
